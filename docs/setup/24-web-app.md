# 24 · `apps/web` — TanStack Start + oRPC

> The entire transport layer. Nine files in `src/server/`, plus routes that compose rather than implement.

**Delivers:** A running fullstack app where every handler is three lines, auth is mounted, and all four enforcement surfaces share one `can()`.

**Prerequisite:** [23 · `@loadbearing/feature`](23-feature-package.md)

**Two directories, and the split is the whole layout.** `src/server/` is every line of transport
logic — the container, CORS, the oRPC base and handler. `src/route/` is pages, plus two files that
do nothing but hand a `Request` to `src/server/`. Nothing in `route/` *implements* an API and
nothing in `server/` renders.

> [!IMPORTANT]
> **The API endpoints are TanStack Start server routes, and an earlier revision of this document had
> them wrong.** It claimed `createServerFileRoute` "does not exist in this version of Start" and
> mounted them through Nitro instead, with `nitro({ serverDir: "src/server", routesDir: "route" })`.
> The API had been *renamed*, not removed: it is the `server` property on `createFileRoute`, and it
> has been there since 1.16x.
>
> That mistake worked — `pnpm build` really did register `/api/auth/**` and `/api/rpc/**` — which is
> why it survived. What it cost is portability. `serverDir` is Nitro's own file scanning, and Nitro
> is one deployment target among several: swap `nitro()` for `@cloudflare/vite-plugin` or
> `@netlify/vite-plugin-tanstack-start` ([hosting](https://tanstack.com/start/latest/docs/framework/react/guide/hosting))
> and nothing scans that directory. The endpoints do not 500 — they stop existing, with no error at
> build time and a 404 at runtime.
>
> A Start server route is in the route tree, so it ships wherever the app ships.

**`src/server/` is still the entire transport layer**, and that is what moves to `apps/api` if
NestJS ever arrives. The two files in `route/api/` are the seam, not the layer — three lines each,
web-standard `Request → Response`, and they are what a Nest controller replaces.

## Step 24.1 — Scaffold

```bash
cd apps
pnpm dlx create-start-app@latest web --framework React --blank --no-install --no-toolchain -y
cd web
node -e "require('fs').rmSync('.git', { recursive: true, force: true })"
rm -f pnpm-workspace.yaml README.md .gitignore && rm -rf .vscode .cta.json
cd ../..
```
> `--blank` skips the demo UI, Tailwind and devtools; `--no-toolchain` skips its lint setup, because lint is root-only here; `--no-install` keeps it out of the workspace's dependency graph until the `package.json` has been rewritten. `rmSync` is the cross-platform `rm -rf` and removes the nested Git repo the scaffolder creates, and the scaffold's own `pnpm-workspace.yaml` **must** go or pnpm treats the app as a second workspace root.
>
> **The CLI now warns that `create-start-app` is deprecated** in favour of `tanstack create` / `npx @tanstack/cli create`. It still works; expect the name to change.

**Then rewrite `package.json` entirely** — the scaffold pins `latest` for the TanStack packages and its own TypeScript, Vite and `@types/*` versions, none of which match the catalog. Keep the scaffold's dependency *set*, replace every version with `catalog:`, and set `"name": "@loadbearing/web"`. `syncpack lint` is what catches a missed one.

Set `"name": "@loadbearing/web"` in `apps/web/package.json`, then:

```bash
pnpm add --filter @loadbearing/web \
  @loadbearing/contracts@workspace:* @loadbearing/permissions@workspace:* \
  @loadbearing/api-client@workspace:* @loadbearing/query@workspace:* \
  @loadbearing/content@workspace:* @loadbearing/ui@workspace:* @loadbearing/feature@workspace:* \
  @loadbearing/composition@workspace:* @loadbearing/application@workspace:* @loadbearing/auth@workspace:* \
  @loadbearing/errors@workspace:* @loadbearing/observability@workspace:* \
  @orpc/server@catalog: @orpc/client@catalog: @tanstack/react-query@catalog: zod@catalog:
```
> `@orpc/server` is here because the oRPC handler lives in `apps/web/src/server/` — this is the fullstack app, so it holds both sides. `composition`, `application`, and `auth` are server-only; the Biome boundary from [05](05-lint-and-format.md) restricts them to `src/server/**`, and that stays **one glob** even though the endpoints live in `src/route/api/` — those two files import `~/server/…`, never a server-only package directly. `nitro` is a dependency too, but only `vite.config.ts` names it now.

**`apps/web/tsconfig.json`** — replace the generated one:

```json
{
  "extends": "@loadbearing/tsconfig/react.json",
  "compilerOptions": {
    "verbatimModuleSyntax": false,
    "types": ["vite/client", "node"],
    "paths": { "~/*": ["./src/*"] }
  },
  "include": ["src/**/*.ts", "src/**/*.tsx", "web.d.ts"]
}
```

> [!IMPORTANT]
> **`verbatimModuleSyntax` is off here, and only here.** The shared base in
> [04](04-typescript-configs.md) turns it on, which is right for a package that emits `dist/` — the
> import you wrote is the import that ships. TanStack Start documents it as a **client/server
> bundle-leak risk** for an app: the flag keeps an import statement whose bindings are all types, so
> `import type { Container } from "@loadbearing/composition"` in an isomorphic file becomes a real
> edge in the client graph rather than nothing at all.
>
> `web.d.ts` is in `include` because it is above `src/` and emits nothing, so no glob would pick
> it up.

**`apps/web/vite.config.ts`**

```ts
import { tanstackStart } from "@tanstack/react-start/plugin/vite";
import viteReact from "@vitejs/plugin-react";
import { nitro } from "nitro/vite";
import { defaultClientConditions, defaultServerConditions, defineConfig } from "vite";

// A function config, because one line has to differ between `vite dev` and `vite build`.
export default defineConfig(({ command }) => {
  const devCondition = command === "serve" ? ["development"] : [];

  return {
    resolve: { tsconfigPaths: true, conditions: [...devCondition, ...defaultClientConditions] },
    ssr: {
      resolve: {
        conditions: [...devCondition, ...defaultServerConditions],
        externalConditions: [...devCondition, ...defaultServerConditions],
      },
      noExternal: [/^@loadbearing\//],
    },
    plugins: [
      // Must come before `viteReact()`.
      tanstackStart({
        router: { routesDirectory: "route", generatedRouteTree: "route-tree.gen.ts" },
      }),
      // Deployment target only, deliberately unconfigured — see the note under Layout.
      nitro(),
      viteReact(),
    ],
  };
});
```

> [!CAUTION]
> **The `development` condition has two traps, and an earlier revision of this document walked into
> both.** It read `conditions: ["development"]` — flat, in every mode.
>
> **1 — It must be dev-only.** Vite's default lists *end* with `development|production`, a token Vite
> expands to `production` during a build. A literal `"development"` has no such behaviour, so it
> survives into `vite build` and picks the **development** entry of any dependency that publishes
> one. `@tanstack/react-router` publishes one, so the production client bundle shipped its dev build
> — visible as `HeadContent.dev.js`'s `data-tanstack-router-dev-styles` filter in
> `.output/public/assets/index-*.js`. Nothing warns; the app works, slightly wrong and slightly
> bigger, forever.
>
> **2 — It must be prepended, not assigned.** The array *replaces* the defaults. Writing
> `["development"]` throws away `browser` on the client and `node` on the server (and
> `["node", "module-sync"]` for `externalConditions`), so any dependency with a browser- or
> Node-specific export map silently resolves to the wrong one.
>
> `[...devCondition, ...defaultClientConditions]` fixes both. If resolution ever misbehaves, drop
> `devCondition` entirely: you fall back to consuming `dist/`, which still works with a rebuild
> between edit and reload.

> [!CAUTION]
> **Two more things in that plugin block each cost a confusing failure, and neither error names the
> cause.**
>
> **The Start plugin owns route generation, and it does not read `tsr.config.json`.** Pointing only
> that file at a custom directory leaves the plugin looking in `src/routes/`, and the build dies with
> `TypeError: Cannot convert undefined or null to object` inside `start-manifest-plugin` — naming
> neither the file nor the directory. Delete `tsr.config.json` and configure the plugin: one
> generator, one config.
>
> **Those paths are relative to `srcDirectory` (`src`), not the project root.** Writing `"src/route"`
> produces `ENOENT … apps/web/src/src/route`.
>
> The directory is `route/`, singular, because this repository's folder rule is non-plural
> ([Folders](../opinions/folders.md)). The framework default is `routes/`, and this is the knob that
> reconciles them.

> [!NOTE]
> **No lint config in the app.** The server-only boundary and the `env.ts` exemption are both `overrides` blocks in the root `biome.json` ([05](05-lint-and-format.md)), keyed on `apps/web/src/server/**` and `apps/*/src/env.ts`. Adding a config here would let the app opt itself out of the rules that exist to constrain it.

## Step 24.2 — `Env`, and the client-safe half of it

> [!CAUTION]
> **This step shipped the worst bug in the kit, and the shape of the mistake is more useful than the
> fix.** `Env` exposed two convenience accessors — `Env.apiUrl` and `Env.authUrl` — and the obvious
> callers were `router.tsx` and `sign-in.tsx`. Both are **isomorphic**. Everything in a TanStack
> Start app is isomorphic unless something says otherwise, so importing `Env` for one string put the
> whole file in the client graph.
>
> What the browser then received was the entire server configuration surface —
> `DATABASE_URL`, `AUTH_SECRET`, `S3_SECRET_KEY`, every variable name — followed by
> `static parsed = Schema.parse({})`, because Vite replaces the environment object with an empty one
> in a client bundle. That is a `ZodError` thrown at module evaluation, before the first render:
> **the app could not hydrate at all.** No value leaked; the names did, and the app was dead.
>
> Three things missed it. `pnpm typecheck` passes — the types are identical in both environments.
> `pnpm build` passes — a bundle that throws at runtime is a valid bundle. And the bundle-leak grep
> in [26](26-hygiene-and-ci.md) passed, because it looks for `drizzle-orm`, `ioredis` and friends,
> and `Env` imports none of them. **A file can be server-only without importing anything
> server-only.**
>
> The fix is two files and one marker import, below.

**`apps/web/src/env.ts`**

```ts
// Start's import-protection plugin fails the *build* when a module carrying this marker is
// reachable from the client graph, naming the file and line. That is the guarantee a naming
// convention cannot give. Filenames ending `.server.ts` get it for free; this file keeps its
// name so the `apps/*/src/env.ts` globs in `biome.json` and `check-architecture.mjs` still
// mean what they say, and takes the marker instead.
import "@tanstack/react-start/server-only";
import { z } from "zod";

const Schema = z.object({
  // `z.url()`, not `z.string().url()` — the chained form is removed in Zod 4.
  DATABASE_URL: z.url(),
  REDIS_CACHE_URL: z.url(),
  REDIS_QUEUE_URL: z.url(),

  S3_ENDPOINT: z.url(),
  S3_REGION: z.string().min(1),
  S3_BUCKET: z.string().min(1),
  S3_ACCESS_KEY: z.string().min(1),
  S3_SECRET_KEY: z.string().min(1),
  S3_FORCE_PATH_STYLE: z.enum(["true", "false"]).transform((v) => v === "true"),

  AUTH_SECRET: z.string().min(32),
  AUTH_URL: z.url(),
  AUTH_TRUSTED_ORIGINS: z.string().transform((v) => v.split(",").map((s) => s.trim())),
  AUTH_SESSION_MAX_AGE_SECONDS: z.coerce.number().int().positive(),
  // The revocation window. Capped in the schema, not by convention — a deploy that
  // raises it to "improve cache hit rate" fails at boot instead of quietly widening
  // the gap between removing access and access stopping.
  AUTH_COOKIE_CACHE_MAX_AGE_SECONDS: z.coerce.number().int().positive().max(60),
  AUTH_REQUIRE_EMAIL_VERIFICATION: z
    .enum(["true", "false"])
    .default("true")
    .transform((v) => v === "true"),

  // `none` searches the chunk text and calls nobody. `openai` and `gemini` embed and need
  // the key; the shipped schema refuses a provider with no key at boot.
  EMBEDDING_PROVIDER: z.enum(["none", "openai", "gemini"]).default("none"),
  EMBEDDING_API_KEY: z.string().min(1).optional(),
  EMBEDDING_MODEL: z.string().min(1).optional(),
  EMBEDDING_DIMENSIONS: z.coerce.number().int().positive().default(1536),

  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
  LOG_PRETTY: z.enum(["true", "false"]).default("false").transform((v) => v === "true"),
  // Two of the four log labels. Low-cardinality by construction.
  APP: z.string().default("web"),
  ENV: z.string().default("development"),

  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
});

export class Env {
  private constructor() {}

  private static readonly parsed = Schema.parse(process.env);

  public static get isProduction(): boolean {
    return Env.parsed.NODE_ENV === "production";
  }

  // The absolute base Better Auth signs cookies and builds callback URLs against. **Server
  // only** — the browser gets `Endpoint.auth` instead. There is deliberately no `apiUrl`
  // here any more: a client-facing accessor on this class is the whole bug above.
  public static get authUrl(): string {
    return `${Env.parsed.AUTH_URL}/api/auth`;
  }

  // The one origin allowlist. Better Auth's CSRF check and CORS both read it.
  public static get trustedOrigins(): readonly string[] {
    return Env.parsed.AUTH_TRUSTED_ORIGINS;
  }

  public static containerConfig() {
    const e = Env.parsed;
    return {
      database: { url: e.DATABASE_URL },
      redis: { cacheUrl: e.REDIS_CACHE_URL, queueUrl: e.REDIS_QUEUE_URL },
      storage: {
        endpoint: e.S3_ENDPOINT,
        region: e.S3_REGION,
        bucket: e.S3_BUCKET,
        accessKey: e.S3_ACCESS_KEY,
        secretKey: e.S3_SECRET_KEY,
        forcePathStyle: e.S3_FORCE_PATH_STYLE,
      },
      auth: {
        secret: e.AUTH_SECRET,
        baseUrl: e.AUTH_URL,
        trustedOrigins: e.AUTH_TRUSTED_ORIGINS,
        sessionMaxAgeSeconds: e.AUTH_SESSION_MAX_AGE_SECONDS,
        cookieCacheMaxAgeSeconds: e.AUTH_COOKIE_CACHE_MAX_AGE_SECONDS,
        requireEmailVerification: e.AUTH_REQUIRE_EMAIL_VERIFICATION,
      },
      embedding: {
        provider: e.EMBEDDING_PROVIDER,
        dimensions: e.EMBEDDING_DIMENSIONS,
        ...(e.EMBEDDING_API_KEY ? { apiKey: e.EMBEDDING_API_KEY } : {}),
        ...(e.EMBEDDING_MODEL ? { model: e.EMBEDDING_MODEL } : {}),
      },
      logging: { level: e.LOG_LEVEL, pretty: e.LOG_PRETTY, app: e.APP, env: e.ENV },
    } as const;
  }
}
```

**Parse at module load, not on first access.** A missing `AUTH_SECRET` should crash the process at boot with a field path, not produce a 500 on the first sign-in attempt an hour later.

**`AUTH_SECRET` has a minimum length** because a short secret is a real weakness and the schema is the only place anyone will ever check.

**Session lifetimes come from the environment, and the cookie cache is capped here rather than trusted.** A staging box and production do not want the same session length, so these are not literals in a factory. The `.max(60)` on the cookie cache is the load-bearing one: that value *is* the revocation window ([16](16-auth-package.md) §16.9), and the pressure to raise it always arrives as a performance argument. A schema that refuses to boot is a better answer than a comment asking people not to.

**`APP_BASE_URL` is not `AUTH_URL`, and the duplication is deliberate.** `AUTH_URL` is Better Auth's own origin and lives only in this schema. `APP_BASE_URL` is the origin a link *inside a message* points at, and it reaches `ContainerConfig.email.baseUrl` — which the worker also parses, because the worker is what renders the invitation link and it holds no auth configuration at all. Collapsing the two would mean putting an auth block in the worker's schema to serve one string ([the mail pipeline](../../packages/composition/docs/reference/mail-pipeline.md)).

**Not every parsed key reaches `containerConfig()`.** `AUTH_URL` and `AUTH_TRUSTED_ORIGINS` are read by Better Auth's own configuration rather than by an adapter, and they are still validated at boot alongside the rest — one place to fail is the entire point of the schema, and a malformed value found at first use is a value found on a machine nobody is watching.

**`AUTH_TRUSTED_ORIGINS` carries the Tauri origins from the first deployment**, not from whenever the desktop app is built:

```bash
AUTH_TRUSTED_ORIGINS=http://localhost:23000,tauri://localhost,http://tauri.localhost
```

Both Tauri entries, because the webview's scheme differs by platform — `tauri://localhost` on macOS and Linux, `http://tauri.localhost` on Windows. Ship one and the desktop app works for half your team ([30](30-desktop-app.md)).

`Env.trustedOrigins` exists so this list has exactly one reader-facing name. Better Auth's CSRF check consumes it through `containerConfig()` and the CORS layer in Step 24.7 consumes it directly — two consumers, one list. A second hardcoded copy is how one of them goes stale and someone spends an afternoon on a preflight failure.

**This file and `apps/worker/src/env.ts` are the only two `process.env` readers in the repository.** The ESLint rule from [05](05-lint-and-format.md) enforces it, and this method is the boundary where environment becomes `ContainerConfig`.

### `Endpoint` — what isomorphic code is allowed to know

**`apps/web/src/endpoint.ts`**

```ts
export class Endpoint {
  private constructor() {}

  // Same-origin paths: the app is served by the same process that answers them, so there
  // is no host to configure and nothing here reads the environment.
  public static readonly rpc = "/api/rpc";
  public static readonly authPath = "/api/auth";

  public static get auth(): string {
    const origin = typeof window === "undefined" ? "https://ssr.invalid" : window.location.origin;
    return `${origin}${Endpoint.authPath}`;
  }
}
```

**Client code needs two addresses, so it gets two addresses and no schema.** That is the entire
point of the file: there is now nothing on the isomorphic side of the app that could pull `Env` in,
so the marker import in `env.ts` has nothing to reject.

**`Endpoint.auth` is absolute, and the reason is a Better Auth constructor.** Its client resolves
`baseURL` through `new URL()` **eagerly**, so a bare `/api/auth` throws
`BetterAuthError: Invalid base URL` — during SSR, where there is no `location` to resolve against.
The symptom is not an error page: React swallows it into the Suspense boundary and `/sign-in` returns
a `200` with an **empty `<body>`**, which is a genuinely hard hour of debugging.

Every `AuthClient` method runs from a browser event, so the server never issues a request through
that value — it only has to parse. `.invalid` is reserved by [RFC 2606](https://www.rfc-editor.org/rfc/rfc2606)
and is guaranteed never to resolve, so a call that *does* slip into an SSR pass fails loudly and
names the line, instead of quietly reaching whatever else is on localhost.

> [!TIP]
> **The general rule, from Start's own execution-model guide: relative URLs belong to browser-only
> code.** Anything isomorphic — a loader, a route component, `router.tsx` — may run where there is no
> document to resolve against. oRPC's client gets away with `"/api/rpc"` only because it defers
> parsing until a request is actually made.

## Step 24.3 — The container

**`apps/web/src/server/container.ts`**

```ts
import { Container } from "@loadbearing/composition";
import { Env } from "~/env.js";

// One per process, at module scope. Never per request.
export const container = new Container(Env.containerConfig());
```

Module scope means one connection pool, one set of Redis connections, and one Better Auth instance for the process lifetime. Constructing per request would open a pool per request, which exhausts Postgres in about four seconds under load.

Count those pools across instances rather than per process. Forty web instances at ten connections each is four hundred against a `max_connections` that defaults to a hundred. Lite connects straight to Postgres, so that sum is the limit you hit. The code is already safe behind a transaction-mode pooler, and [pgBouncer](../scale/pgbouncer.md) is how to add one ([Data and scale](../opinions/data-and-scale.md) §5).

## Step 24.4 — The oRPC base and principal middleware

**`packages/api-server/src/router/base.ts`** — it began in `apps/web/src/server/orpc/` and moved
to its own package once a second app mounted the same chain; see `packages/api-server/docs/index.md`.

```ts
import type { Principal } from "@loadbearing/application";
import type { Container } from "@loadbearing/composition";
import { ProcedurePermissions } from "@loadbearing/contracts";
import { ForbiddenError, UnauthorizedError } from "@loadbearing/errors";
import { Correlation, type Logger, type TraceId } from "@loadbearing/observability";
import { os } from "@orpc/server";
import { ErrorInterceptor } from "./error.interceptor.js";

// Initial context: environment-shaped, injected once by the adapter.
export const base = os.$context<{ container: Container; headers: Headers }>();

// Execution context: per-request, resolved by middleware.
export const principalMiddleware = base.middleware(async ({ context, next, path }) => {
  const principal: Principal | null = await context.container.principals.fromHeaders(
    context.headers,
  );

  // `AppError`s, not `ORPCError`s, so `errorMiddleware` below logs and shapes them the
  // same way it shapes everything else — an auth failure that short-circuits past the
  // one place that logs is a failure nobody sees. Doc 12's rule holds here too: throw
  // the error, let the adapter map it.
  if (!principal) throw new UnauthorizedError();

  // Defence in depth — fails closed on any procedure with no permission mapping.
  const required = ProcedurePermissions.required(path.join("."));
  if (!required) throw new ForbiddenError(path.join("."));

  return next({ context: { principal } });
});

// The one place every server-side failure becomes a transport error, and it is a
// **middleware** rather than an adapter interceptor. That is not a style choice: oRPC's
// `clientInterceptors` see only the *initial* context, so an interceptor there has no
// `traceId` and no request-scoped logger to hand `ErrorInterceptor`.
//
// Declared against what it requires rather than derived from the chain above —
// `BuilderWithMiddlewares` has no `.middleware()`, so a middleware that depends on an
// earlier one states its own context and oRPC checks the chain supplies it.
export const errorMiddleware = os
  .$context<{ traceId: TraceId; log: Logger }>()
  .middleware(async ({ context, next }) => {
    try {
      return await next();
    } catch (thrown) {
      ErrorInterceptor.toTransport(thrown, context.log, context.traceId);
    }
  });

// Before `principalMiddleware`, so a failure to resolve a principal is already
// correlated. Both entrypoints pass the raw `Headers`, so nothing upstream changes.
export const correlationMiddleware = base.middleware(async ({ context, next }) => {
  const traceId = Correlation.fromHeaders(context.headers);
  return next({ context: { traceId, log: context.container.logger.child({ traceId }) } });
});

// Built from `implement(contract)` rather than from `base`, so it carries the
// contract's own shape and a router writes `authed.role.list.handler(...)` with the
// procedure's input and output types already known.
export const authed = implement(contract)
  .$context<{ container: Container; headers: Headers }>()
  .use(correlationMiddleware)
  .use(errorMiddleware)
  .use(principalMiddleware);
```

> [!CAUTION]
> **`implement(contract.role.list).use(authed)` looks like the same thing and is not.** `.use()` takes
> a *middleware*; `authed` is a builder. Passing one produces several hundred characters of failed
> inference naming `MergedCurrentContext` rather than a sentence, and the next error says `container`
> does not exist on the context. Build `authed` from the contract once, here, and let routers index
> into it.

**The trace id is a child logger, not ambient state.** `AsyncLocalStorage` would be Node-only, and doc 17 rule 2 forbids request-scoped state on the `Container`. A child bound with `{ traceId }` travels the same path the `Principal` already travels, and every line a handler writes carries it without naming it again.

`Correlation.fromHeaders` adopts an upstream `x-request-id` where a proxy set one — sanitised first, because it arrives from the network and then rides every line of the request — and mints a `Uuid.v7()` otherwise.

**The middleware calls `PrincipalBuilder`, never Better Auth directly.** That is what keeps the transport layer ignorant of the auth library, and it is why a NestJS migration rewrites a guard rather than rewriting authentication.

**Creating an `authed` base that already includes the middleware** means protected procedures cannot forget it. Anything built on `base` instead of `authed` is unauthenticated on purpose and should be obvious in review.

**The `ProcedurePermissions` check fails closed.** A procedure with no mapping is denied, not allowed. Paired with the coverage test in [10](10-contracts-package.md), forgetting to map a new procedure is caught at test time and, failing that, at request time — never by shipping an ungated endpoint.

**`authed` chains a second middleware after the principal one, and the order is the point.**
`shardMiddleware` calls `container.placed(principal, next)` — one `keyOf`, one `resolve`, into an
`AsyncLocalStorage` scope for the rest of the request. It cannot run before the principal exists,
and a routed repository reached without it throws rather than guessing a node. Because `authed`
chains it, a protected procedure cannot forget to be placed; a procedure built on `base` is
unauthenticated *and* unplaced, which is the same "obvious in review" property.

**A streaming procedure needs `AsyncLocalStorage.snapshot()` and this is the one place it shows.**
An async generator's frames resume outside the scope that created them, so without the snapshot
every frame after the first — and in practice the first too — resolves no shard. The middleware
wraps the iterable's `next`, `return` and `throw` in the restored scope. See
[sharding](../../packages/infrastructure/docs/reference/sharding.md).

**This is not the real gate.** `Authorizer.assert()` inside the use-case is. The worker bypasses this middleware entirely, and so does any SSR direct call that skipped the adapter. Two checks, and only one of them is on every path.

## Step 24.5 — The error interceptor

**`packages/api-server/src/router/error.interceptor.ts`**, moved with the chain above.

```ts
import { ErrorNormalizer, HTTP_STATUS } from "@loadbearing/errors";
import type { Logger } from "@loadbearing/observability";
import { ORPCError } from "@orpc/server";

export class ErrorInterceptor {
  private constructor() {}

  public static toTransport(thrown: unknown, log: Logger, traceId: string): never {
    const error = ErrorNormalizer.normalize(thrown);

    // The one place every server-side failure passes through, so the one place
    // that has to log it. `failure` reads the severity for its level and keeps the
    // non-enumerable `cause` that `toJSON()` cannot reach.
    log.failure(error);

    throw new ORPCError(error.code, {
      status: HTTP_STATUS[error.code],
      data: { ...error.toJSON(), traceId },
    });
  }
}
```

**Three lines, and no `CODE_MAP`.** `normalize()` guarantees an `AppError` for anything thrown — a `ZodError`, a Postgres failure, a rejected string — so there is no fall-through branch to get wrong, and `HTTP_STATUS` is total over `ErrorCode` so a new code cannot ship without a status ([09](09-errors-package.md)).

**The body is the envelope, not prose.** `error.toJSON()` sends `{ code, context, fields? }`, which the client reconstructs into the same class and renders through `content` in its own locale. The server has no opinion about the wording and never needs one.

**The envelope carries the trace id, and that is what makes it worth minting.** `ErrorEnvelope.traceId` was declared from the first draft of `errors` and left unpopulated; this is the line that fills it. `AppError.from()` reads it back on the client and `TransportError` keeps it, so an error page can show a reference string. A user who says "it broke around two" hands over eight characters instead of a timestamp range.

**Nothing unmapped can leak.** The old failure mode — a Postgres error string in a client response telling an attacker your table names — is closed at the normaliser rather than guarded against here: an unrecognised throw becomes `INTERNAL`, and the original is kept on a non-enumerable `cause` for the logger where `toJSON()` cannot reach it.

## Step 24.6 — A router

**`apps/web/src/server/orpc/task.router.ts`** — illustrative. The kit ships two real routers built exactly this way, `role.router.ts` and `member.router.ts` ([27](27-verification-and-first-feature.md) Step 27.4).

```ts
import { authed } from "../import.js"; // `@loadbearing/api-server`, re-exported

export class TaskRouter {
  private constructor() {}

  public static readonly reactivate = authed.task.reactivate.handler(({ input, context }) =>
    context.container.task.reactivate.execute(context.principal, input),
  );

  public static readonly create = authed.task.create.handler(({ input, context }) =>
    context.container.task.create.execute(context.principal, input),
  );

  // What `app.router.ts` mounts, mirroring the slice's `Procedures.all`.
  public static readonly all = {
    reactivate: TaskRouter.reactivate,
    create: TaskRouter.create,
  } as const;
}
```

**Three lines per procedure**: pull the use-case off the container, call `execute` with the principal and validated input, return the result. No business logic, no authorization decision, no error mapping. That is the entire transport layer for a feature, and it is what makes swapping to NestJS a rewrite of *these files* and nothing else.

**`apps/web/src/server/orpc/app.router.ts`**

```ts
import { MemberRouter } from "./member.router.js";
import { RoleRouter } from "./role.router.js";

export const appRouter = { role: RoleRouter.all, member: MemberRouter.all };
```

The shape mirrors `contract` exactly. A mismatch is a type error, and the merge point is the only
line a new slice adds here.

> [!NOTE]
> **One procedure in `member.router.ts` is four lines rather than three, and it is worth knowing
> why.** `revokeInvitation` awaits the use-case and returns `{ ok: true }` — the use-case answers
> `void`, because "it worked" is the transport's word and not the domain's. A use-case that returned
> `{ ok: true }` would be shaping a response for a protocol it must not know about; a router that
> returned `undefined` would make the contract's output schema a lie. The four lines are where those
> two facts meet, and every write-shaped procedure will have them.

> [!NOTE]
> **One procedure is not a request at all.** `realtime.stream` is an `async function*` whose
> output contract is `eventIterator(RealtimeContract.message)`, and `RPCHandler` serves it as
> `text/event-stream` on this same `/api/rpc` route — no second route, no second handler, no new
> dependency. It takes no input, because its channel is built from the principal
> `principalMiddleware` already resolved; there is nothing to ask for and so nothing to get wrong.
> The full account, including why it is a POST despite the contract's `GET` and why
> `http.request.completed` fires at stream start, is in
> [`apps/web/docs/reference/server-functions.md`](../../apps/web/docs/reference/server-functions.md).

## Step 24.7 — The HTTP entrypoints

> [!IMPORTANT]
> **API routes are the TanStack route tree's.** A file route carries a `server` property alongside
> `component`, and its `handlers` map takes `GET`/`POST`/…/`OPTIONS` — plus `ANY`, which is the one
> this app wants, because both handlers dispatch on method themselves.
>
> Whatever you do here, verify it against the **installed** version rather than a snippet: this API
> was `createServerFileRoute` for a while, then moved onto `createFileRoute`. `@tanstack/react-start`
> now ships its own agent skills under `node_modules/@tanstack/react-start/skills/`, and
> `start-core/server-routes/SKILL.md` is the current contract in the exact version you installed —
> a better source than any document, this one included.
>
> The good news is that it moves *less* than it looks: both handlers are web-standard
> `Request → Response` functions, and these two files are the three lines that bind them to a router.
> That is the same property that makes a Nest migration cheap.

**`apps/web/src/server/orpc/handler.ts`** builds the handler once, for the process — building it per
request rebuilds the router's match table on every call:

```ts
const handler = new RPCHandler(appRouter, {});

export async function handleRpc(request: Request): Promise<Response> {
  const preflight = Cors.preflight(request);
  if (preflight) return preflight;

  const { matched, response } = await handler.handle(request, {
    prefix: "/api/rpc",
    context: { container, headers: request.headers },
  });

  return Cors.apply(request, matched ? response : new Response(null, { status: 404 }));
}
```

**No context annotation.** oRPC infers the initial context from the procedures the router holds.
An *empty* `appRouter` gives it nothing to infer from and does need
`new RPCHandler<{ container: Container; headers: Headers }>(...)` — which is what the kit carried
until the first slice landed. Once one has, restating it here only lets the two drift.

**`apps/web/src/route/api/rpc/$.ts`** and **`src/route/api/auth/$.ts`** mount them:

```ts
import { createFileRoute } from "@tanstack/react-router";
import { handleRpc } from "~/server/orpc/handler.js";

export const Route = createFileRoute("/api/rpc/$")({
  server: { handlers: { ANY: ({ request }) => handleRpc(request) } },
});
```

```ts
export const Route = createFileRoute("/api/auth/$")({
  server: {
    handlers: {
      ANY: async ({ request }) => {
        const preflight = Cors.preflight(request);
        if (preflight) return preflight;

        return Cors.apply(request, await container.auth.handler(request));
      },
    },
  },
});
```

**Four things about those two files.**

`request` is a standard `Request` and the handler returns a standard `Response`. Better Auth speaks
the Fetch API and oRPC's fetch adapter does too, so both drop straight in — and the router
underneath them is replaceable.

**`$.ts` is a splat**, which is what `/api/rpc/*` and `/api/auth/*` need: oRPC addresses a procedure
as a path segment and Better Auth mounts a dozen sub-paths. `handleRpc` still passes
`prefix: "/api/rpc"` so oRPC strips it before matching.

**`ANY`, not `POST` and `OPTIONS` separately.** `Cors.preflight` already answers `OPTIONS` and
`handleRpc` already 404s an unmatched procedure, so splitting the method here would put the same
decision in two places.

**These files have no `component`.** A route may be server-only; nothing renders at `/api/rpc/$`.

### The third entrypoint: `/api/health`

**`apps/web/src/route/api/health.ts`** is the one route an orchestrator reaches before any credential
exists, so it is unauthenticated by necessity rather than by oversight.

```ts
export const Route = createFileRoute("/api/health")({
  server: {
    handlers: {
      GET: async () => {
        const report = await container.health();

        return new Response(JSON.stringify(report), {
          status: report.healthy ? 200 : 503,
          headers: { "content-type": "application/json", "cache-control": "no-store" },
        });
      },
    },
  },
});
```

**Readiness, not liveness**, and the difference decides what the platform does with the answer. A 503
means *do not send me traffic yet* — a rolling deploy holds the new instance out of the pool until
Postgres and Redis answer. A liveness probe returning 503 gets the container killed
instead, which is the wrong response to a database that is still starting.

**`cache-control: no-store` is not boilerplate.** A cached readiness answer keeps reporting healthy
for its TTL after the thing it describes has stopped, which is precisely the window a load balancer
uses to route traffic into a broken instance.

**`container.health()` checks every Postgres node and the cache and queue Redis roles in parallel.**
In lite both roles are one Redis, so it is asked twice. `analytics` is always `null`: lite runs no
analytics store, which is neither healthy nor degraded ([Analytics](../scale/analytics.md) brings one
back). No log collector is in the list either: logs are lossy by design
([Data and scale](../opinions/data-and-scale.md)), so a collector being down would not be a reason
to drain an instance that is serving requests correctly.

> [!WARNING]
> **A route `beforeLoad` does not protect an API route.** These are the paths into `src/server/`, and
> everything behind them authenticates for itself — `principalMiddleware` for oRPC, Better Auth for
> its own endpoints, and `/api/health` deliberately not at all. Test each one with a direct anonymous
> request and assert nothing private comes back; that is the check in the Gate below.

### CORS, because the desktop client is cross-origin

A Tauri webview is served from a custom protocol, so **every** call it makes to these two routes is cross-origin — there is no configuration that makes it same-origin. Both handlers need a CORS layer, and it reads the same allowlist as the CSRF check:

**`apps/web/src/server/cors.ts`**

```ts
import { Env } from "~/env.js";

export class Cors {
  private constructor() {}

  private static headersFor(origin: string | null): Headers {
    const headers = new Headers();
    if (!origin || !Env.trustedOrigins.includes(origin)) return headers;

    headers.set("Access-Control-Allow-Origin", origin);
    headers.set("Access-Control-Allow-Credentials", "true");
    headers.set("Access-Control-Allow-Headers", "content-type,authorization,x-api-key");
    headers.set("Access-Control-Allow-Methods", "GET,POST,OPTIONS");
    headers.set("Vary", "Origin");
    return headers;
  }

  // Preflight. Returns null when the request is not one.
  public static preflight(request: Request): Response | null {
    if (request.method !== "OPTIONS") return null;
    return new Response(null, { status: 204, headers: Cors.headersFor(request.headers.get("origin")) });
  }

  public static apply(request: Request, response: Response): Response {
    for (const [key, value] of Cors.headersFor(request.headers.get("origin"))) {
      response.headers.set(key, value);
    }
    return response;
  }
}
```

Wire it into both entrypoints — answer the preflight first, then decorate the real response:

```ts
const preflight = Cors.preflight(request);
if (preflight) return preflight;
return Cors.apply(request, await container.auth.handler(request));
```

Four things that matter more than they look:

**Echo the origin, never reflect it blindly.** `Access-Control-Allow-Origin` is set only for an origin already on the allowlist. Reflecting whatever arrived, with `Allow-Credentials: true`, is a hole large enough to drive a CSRF through — and the two headers are specified never to be combined with `*` for exactly that reason.

**`Vary: Origin` is not optional.** Without it any cache in front of this — a CDN, a reverse proxy — can serve one origin's CORS response to another origin and the failure looks random.

**`Allow-Credentials: true` and `Allow-Headers: authorization` are both required**, because the web client authenticates with a cookie and the desktop client with a bearer token, against the same two routes ([16](16-auth-package.md), [18](18-api-client-package.md)).

**`x-api-key` is in the list** because `PrincipalBuilder` checks it first ([16](16-auth-package.md)); omitting it means integrations calling from a browser context fail preflight with a message that does not mention the header.

> **Check the current oRPC fetch-adapter and TanStack Start server-route signatures against the version you installed.** Both are version-sensitive, and these are the two files where copying a stale snippet costs an afternoon — this document has already been wrong about them once. The *contract* — mount a fetch handler, inject `{ container, headers }`, intercept errors — is stable; the API surface is not. `node_modules/@tanstack/react-start/skills/` is the version-accurate source.

## Step 24.8 — SSR without a network hop

During SSR the app must not call its own HTTP endpoint. `"/api/rpc"` resolves to your own server, so each loader would round-trip through the loopback interface — serialising and deserialising the same payload twice and competing with real user requests for the connection pool. Six loaders means six self-requests before a byte renders.

**`apps/web/src/server/rpc-client.ts`**

```ts
import { createRouterClient } from "@orpc/server";
import { container } from "./container.js";
import { appRouter } from "./orpc/app.router.js";

export function createServerRpcClient(request: Request) {
  return createRouterClient(appRouter, {
    context: { container, headers: request.headers },
  });
}
```

`createQueryClient()` chooses per environment — `ApiClient.inProcess(...)` on the server, `ApiClient.overHttp(...)` in the browser. Both satisfy the same contract type, so loaders and components cannot tell which they got, and client-side navigation picks up the HTTP client automatically.

**Two rules keep this honest:**

**Pass the real request headers.** `principalMiddleware` resolves the principal from them. Skipping them because "we are already on the server" either breaks auth or invites someone to construct a privileged principal directly. In-process skips serialisation, nothing else — same middleware, same `Authorizer.assert()`.

**Loaders talk to `ApiClient`, never to `appRouter`.** A loader importing the router is importing server code that will not exist once NestJS owns the API, and every loader would then need touching. Going through the client means one factory changes instead.

## Step 24.9 — Route and UI gating

**`apps/web/src/route/-guard.ts`**

```ts
import { redirect } from "@tanstack/react-router";
import type { CapabilitySet, PermissionKey } from "@loadbearing/permissions";

export class RouteGuard {
  private constructor() {}

  public static requirePermission(permission: PermissionKey, goalId?: string) {
    return ({ context }: { context: { capabilities: CapabilitySet } }): void => {
      if (!context.capabilities.can(permission, goalId)) {
        throw redirect({ to: "/forbidden" });
      }
    };
  }

  public static requireSession() {
    return ({ context }: { context: { user: { id: string } | null } }): void => {
      if (!context.user) throw redirect({ to: "/sign-in" });
    };
  }
}
```

Used in a route's `beforeLoad`. Same `CapabilitySet.can()` the server calls — that identity is the entire point.

**The `-guard.ts` filename leads with a hyphen** because TanStack Start's file-based routing treats `-`-prefixed files as non-routes. Framework naming wins inside `src/route/`.

> [!IMPORTANT]
> **`throw redirect(...)` fails `@typescript-eslint/only-throw-error`**, because a `Redirect` is not
> an `Error` — deliberately, since the router catches it as control flow rather than as a failure.
> The rule is right in general and wrong here, so [05](05-lint-and-format.md) turns it off for
> `apps/*/src/route/**` and nowhere else. `src/server/**` keeps it: a transport handler throwing a
> non-Error is a real bug.
>
> **No `search` on the redirect.** `redirect({ to: "/forbidden", search: { permission } })` requires
> `/forbidden` to declare a search schema, and a permission key in the URL is a detail the page does
> not need — the four enforcement surfaces have already decided the answer.

## Step 24.10 — Messages in the SSR payload

Copy reaches the browser the same way the session does: resolved on the server, embedded in the
first response, never fetched. The difference is that copy is *split* — a route takes the
namespaces it reads from and no others ([20](20-content-package.md)).

### A route declares its namespaces

**`apps/web/src/route/-messages.ts`**

```ts
import type { ClientNamespace, MessageStore } from "@loadbearing/content";

declare module "@tanstack/react-router" {
  interface StaticDataRouteOption {
    // Namespaces this route's subtree may call t() with, beyond the shell.
    readonly messages?: readonly ClientNamespace[];
  }
}

export interface MessageRouterContext {
  readonly messages: MessageStore;
}
```

**`apps/web/src/route/(shell)/sign-in.tsx`**

```tsx
const MESSAGES = ["auth"] as const satisfies readonly ClientNamespace[];

export const Route = createFileRoute("/sign-in")({
  staticData: { messages: MESSAGES },
  loader: ({ context }) => context.messages.ensure(MESSAGES),
  component: SignInPage,
});
```

A route that also loads data resolves both at once — the namespace chunk and the API call are
independent, so serialising them costs a round trip for nothing:

```ts
loader: async ({ context, params }) => {
  const [, task] = await Promise.all([
    context.messages.ensure(MESSAGES),
    context.api.task.get({ id: params.taskId }),
  ]);

  return { task };
},
```

**The declaration is one local `const` referenced twice, not a helper.** `staticData` is what a
prefetcher or a coverage test can read without executing anything; the loader is what actually
resolves it. Deriving one from the other means reaching into `ctx.route.options`, which is
version-sensitive in exactly the way Step 24.8 already warns about — and the duplication is one
identifier in one file.

**The `-` prefix keeps `-messages.ts` out of the route tree**, the same convention as
`-guard.ts` below.

### The root route ensures the shell

```tsx
// apps/web/src/route/__root.tsx
loader: ({ context }) => context.messages.ensure(ContentSource.SHELL),
```

> [!CAUTION]
> **Do not skip this, and do not believe the sentence this document used to lead with.** It said
> `common` needs no declaration because "every `ContentSource` puts it in every snapshot" — which is
> true of every *fetch* and therefore says nothing about a route that never fetches.
>
> `MessageStore.empty()` starts at `namespaces: []`, and `ensure()` returns early when nothing is
> missing. So `/` and `/forbidden` — which declare no namespaces of their own — reached `t()` with an
> empty catalog and rendered **raw message keys**: the home page shipped the literal string
> `state.empty`. `/sign-in` never showed it, because `ContentSource.resolve()` unions the shell into
> the `auth` fetch, which is exactly why the bug survived review.
>
> The root loader runs before every child loader and `dehydrate()` runs after all of them, so the
> snapshot in the SSR payload is still the union of the shell plus the entry path.

### The server builds a store per request

**`apps/web/src/router.tsx`**

```tsx
// Start calls this per request on the server and once in the browser, which is exactly
// the lifetime every object below wants. There is no `deps` parameter and no separate
// client/server entry to keep in step — the factory *is* the boundary.
export function getRouter() {
  const content = new StaticContentSource();     // CLIENT_CATALOG — no email
  const messages = new MessageStore(content, MessageStore.empty("en"));
  const { queryClient, apiClient } = createQueryClient({
    transport: ApiClient.overHttp(Endpoint.rpc, new CookieAuthStrategy()),
  });

  return createTanStackRouter({
    routeTree,
    defaultPreload: "intent",
    context: { messages, queryClient, api: apiClient },
    dehydrate: (): RouterDehydrated => ({ messages: messages.dehydrate() }),
    hydrate: (payload: RouterDehydrated) => messages.restore(payload.messages),
  });
}

declare module "@tanstack/react-router" {
  interface Register {
    router: ReturnType<typeof getRouter>;
  }
}
```

**A store is constructed per call, never at module scope.** Same reason `createQueryClient` is a
factory ([21](21-query-package.md)): a module-scope store built during one request would serve that
user's locale to the next one. Start calling `getRouter()` per request is what makes that free
rather than something to remember.

> [!NOTE]
> **`MessageStore.empty(locale)`, not `MessageStore.EMPTY`.** It has to be a factory rather than a
> constant because a snapshot carries its locale — and `namespaces: []` is what makes `ensure()`
> fetch whatever the first navigation asks for. Added to `content` in
> [20](20-content-package.md).
>
> **Locale negotiation happens later, in the root route, and that is not a workaround.**
> `Locales.negotiate(acceptLanguage, cookie)` needs the request and `getRouter()` does not receive
> one, so the store is seeded with `Locales.DEFAULT` here and the root's `beforeLoad` calls
> `messages.setLocale()` once `fetchAppearance` has read the header and the cookie. The ordering is
> load-bearing: `beforeLoad` completes before the loader below it, and `ensure()` fetches a
> namespace for whatever locale the store holds when it is called. Reverse the two and the first
> paint is English.
>
> **The locale rides `AppearanceSnapshot`**, beside theme, mode and font — same cookie, same
> server-resolved-so-the-first-byte-is-right argument. It is the one of the four that is not a CSS
> variable, which is why the switcher calls `router.invalidate()`: the copy has to be fetched, not
> restyled.

### Why there is no second fetch

`dehydrate()` runs after every matched route's loader has resolved, so the snapshot it returns
is already the union of the shell plus every namespace on the entry path. TanStack Start
serialises that into the SSR payload alongside the dehydrated `QueryClient`, and `hydrate` runs
before the first client render. **The first client render sees a complete `Translator` — no
fetch, no waterfall, no flash of English.**

That is the same property `SessionProvider` gets from the `CapabilitySetDto` in Step 24.11, by
the same mechanism, for the same reason. Three things ride the SSR payload — the session DTO,
the capability set, and the message snapshot — and they are three instances of one pattern:
**resolve on the server, serialise, render correct on the first byte.**

> [!NOTE]
> **Check `dehydrate`/`hydrate` against your pinned Start version.** The *contract* is stable —
> a JSON object produced after matching, embedded in the payload, handed back before first
> render — but the API surface moves. If it has, the fallback is a
> `<script type="application/json">` in `__root.tsx` read by id at hydration; escape `<` in the
> serialised string. Note the snapshot's *content* is never user input: the only
> user-influenced value is the locale, and `Locales.is()` narrows it to a two-member union
> before it can index a catalog.

### Client-side navigation

`ensure()` is the loader, and `defaultPreload: "intent"` makes TanStack Router run loaders on
hover — alongside prefetching the route's own JavaScript chunk. So a namespace chunk downloads
at the same moment the route chunk does, on the same trigger, and by click time both are warm.
There is nothing else to build.

**`defaultPreload: "intent"` is load-bearing here, not a nicety.** Without it, the first
navigation into a namespace nobody has needed yet resolves its dynamic import *during* the
loader — a visible pause on a route that would otherwise have been instant.

| Where the copy comes from | When |
|---|---|
| Inlined in the HTML payload | shell + the entry route's namespaces, at first paint |
| A prefetched JavaScript chunk | any namespace first needed by a client-side navigation |
| Nowhere | `email` — it never leaves the server ([05](05-lint-and-format.md) Step 5.3) |

## Step 24.11 — The root route

`__root.tsx` is where everything composes. Two API notes first: the root route is
`createRootRouteWithContext<RouterContext>()` so every route sees the per-request objects, and the
document lives in **`shellComponent`** rather than `component` — the older shape renders the
providers inside `<body>` instead of around it.

> [!CAUTION]
> **`shellComponent` receives the matched subtree as `children`. Do not also render an `<Outlet />`.**
> The two are the same thing, and rendering both draws **every page twice** — two `<main>` elements,
> two of every gated control, in one document.
>
> This is the one difference from `component` that reads backwards, so it is worth knowing why.
> `router-core` renders a root match as `<ShellComponent>{…<MatchInner />}</ShellComponent>`, and
> `MatchInner` falls back to `<Outlet />` when the root declares no `component`. The shell wraps that;
> it does not sit inside it. Nothing warns — the page just renders twice — so it is easy to ship:
>
> ```bash
> curl -s http://localhost:23000/ | grep -c "<main"   # must print 1
> ```

In order:

1. `<html lang={locale}>` from the negotiated locale. Screen readers switch voice on it, and browsers pick hyphenation and quote rules from it.
2. Import `@loadbearing/ui/theme.css` and `@loadbearing/ui/class.css`.
3. An inline script in `<head>` applying the stored theme **before** hydration, or dark-mode users get a white flash on every load.
4. `ApiClientProvider` with the environment-appropriate client.
5. `QueryClientProvider` with the per-request or singleton `QueryClient`.
6. `MessageProvider` with the per-request `MessageStore` from the router context — not a bare `Translator`, because client-side navigation adds namespaces after the provider has mounted.
7. `SessionProvider` with the user and the `CapabilitySetDto` resolved during SSR.
8. `{children}` — **and nothing else**, per the caution above.

That seventh one matters: resolving capabilities on the server and serialising the DTO means the first rendered HTML already has correct permission gating. Fetching them client-side means every gated element flashes.

> [!NOTE]
> **How the session actually gets there.** `RouterContext` carries `user`, `capabilities` (as the
> DTO) and a `SessionStore`; `router.tsx` seeds the first two signed-out, and the root route's
> `beforeLoad` replaces them for every route beneath it — `beforeLoad` rather than `loader`, because
> `RouteGuard` runs in a child's `beforeLoad` and only a parent `beforeLoad`'s return value is in
> scope by then.
>
> The value comes from `fetchSession`, a `createServerFn` in `src/server/`. That is one of the few
> things a server function is *for* here: it carries no business logic and makes no authorization
> decision, it only resolves who is asking so the first rendered byte is already gated. `SessionStore`
> rides the same `dehydrate`/`hydrate` payload as the message snapshot, so the browser does no fetch
> of its own — and `/sign-in` calls `session.invalidate()` then `router.invalidate()`, because the
> cookie has changed and nothing else knows.
>
> **The context carries the `CapabilitySetDto`, not a `CapabilitySet`.** TanStack Router dehydrates a
> `beforeLoad` return value into the SSR payload and rejects anything carrying a method at the type
> level. `RouteGuard` rebuilds the class — which keeps `can()` the one decision — and
> `SessionProvider` does the same round trip on the component side.
>
> `empty()` still denies everything, so a guard that somehow ran before the root resolved fails in
> the safe direction: there is no loading state that grants access ([23](23-feature-package.md)).

## Two habits that decide whether a NestJS migration is cheap

**1. Never use `createServerFn` for a business operation.** TanStack server functions are a Start-only transport with no NestJS equivalent, so anything written that way must be *rewritten* rather than moved — and it will be scattered across route files rather than confined to one folder.

```ts
// ✗ has to be rewritten later, and it bypasses the contract entirely
const reactivate = createServerFn().handler(async ({ data }) => { ... });

// ✓ moves to a Nest controller unchanged
TaskRouter.reactivate  // implements contract.task.reactivate
```

Server functions are fine for genuinely framework-local concerns — setting a cookie, issuing a redirect — provided they contain no business logic and no authorization decision.

**2. Route loaders reach the server through `ApiClient`, never the router directly.** Add both to the lint config: `no-restricted-imports` blocking `@tanstack/react-start/server` outside `src/server/**`, and blocking the router module outside the same directory.
